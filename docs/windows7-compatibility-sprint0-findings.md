## Interpretation

There are two independent compatibility tracks:

1. **CSS:** a legacy JavaScript plugin cannot make the current Tailwind 4 output render all its CSS features in Chrome 109. The critical chat surface needs a CSS strategy decision and a real Chrome 109 rendering check.
2. **JavaScript/runtime:** adding a legacy build may help with JavaScript syntax and selected APIs, but React 19, router, design system and chat dependencies need to be verified on the actual target. The current code does not produce a legacy entry today.

The scope decision for this worktree is **basic operator conversation handling**, not full parity for the CRM's admin, automation, journey editor, analytics and integration screens. The selected strategy is a separate Chrome 109 build profile with a dedicated application shell and routes for login and conversations. It reuses the current Auth, permissions and Chat components, with a profile-specific ChatPage wrapper to keep the shared high-resolution-logo loading screen out of the conversation route. It omits the full CRM route table, global notification/plugin shell, guided chat tour and unrelated React Flow stylesheet. The default modern build remains on `index.html`; the legacy build also emits a root `index.html` into `dist-chrome109/` so it can be hosted independently. Chrome 109 supports ES modules, so a `nomodule` bundle is not required for this named baseline; older browsers without module support need a separate loader strategy. The preview must use a separately configured endpoint/API destination.

### Pilot browser support boundary

The dedicated profile targets Chrome 109 as its minimum Chromium version and Windows 7 / Chrome 109 as the release acceptance baseline. Chrome versions below 109, Internet Explorer, Firefox, Safari, embedded webviews and other Chromium-based browsers (including Edge) are outside this pilot until they pass their own runtime and visual checks. The normal `dist/` build and its current modern-browser target remain unchanged. This is the intended support boundary, not a support claim: Chrome 109 on the Windows 7 device is still a release gate. A browser update, where possible, remains the preferred operational choice.

This is a legacy-access bridge with a significant platform risk. Google identifies Chrome 109 as the last version for Windows 7, and its current requirements list Windows 10 or later for supported Windows installations; Microsoft ended Windows 7 support on 14 January 2020. Treat a Windows 7/Chrome 109 pilot as an exception for a controlled, time-limited workflow, with restricted accounts and network access, and plan device migration. The compatibility build cannot restore browser or operating-system security support.

The original screenshot's full cause is not yet established, but a closely related color failure is now reproduced. The HTML bootstrap sets a dark inline canvas (`#0b0f19`); Chromium 109.0.5414.0 reports `CSS.supports()` true for OKLCH and `color-mix()`, and `getComputedStyle()` returns the authored values, yet a direct OKLCH swatch paints almost black. The `@supports not (color: oklch(...))` branch remains inactive. This supports the hypothesis that unsupported or partially implemented design tokens can produce the low-contrast appearance, but the exact final stable Windows Chrome build and original screenshot still need target-machine inspection.

## Compatibility implementation prototype in this worktree

The isolated `src/styles/chrome109.css` stylesheet provides unconditional sRGB light and dark tokens, 68 palette variables used by chat classes, and explicit alpha-color overrides for key login/conversation classes. This choice follows runtime evidence: M109.0.5414.0 accepts the queried color syntax in feature checks but paints a direct OKLCH swatch almost black, so a negative `@supports` query is unreliable and rendering remains partially broken. The stylesheet is imported only by `main.chrome109.tsx`; modern `main.tsx` never requests it. Dark mode uses the same `#0b0f19` canvas as the HTML bootstrap, paired with a light foreground.

Both production builds pass. The normal build does not include the compatibility stylesheet; the dedicated profile emits the sRGB tokens and light/dark alpha overrides after its shared Tailwind CSS. The M109 color probe confirms the profile's design tokens are needed; key primary/muted fills, borders and login gradient stops have explicit fallbacks. Other color-mix utilities and route-specific custom properties remain unverified. Targeted Windows 7 visual QA is still required before claiming the flow is supported.

The `build:chrome109` profile in `vite.chrome109.config.ts` builds a dedicated root `index.html` in `dist-chrome109/`, using the Vite `chrome109` JavaScript target and Lightning CSS targets for CSS. The HTML points to `main.chrome109.tsx`, whose app shell limits its routes to login and conversations, with a clear setup-required message for installations that have not completed initial setup. `i18n/chrome109.ts` registers the existing `auth`, `chat`, `common` and `tours` namespaces for all six supported languages; runtime consumers import a shared i18next instance so the chat chunk does not pull the full multi-product catalog. A local transformer probe showed OKLCH declarations receive sRGB fallback declarations and color-mix enhancements are guarded with feature queries. That is build evidence only; the new direct M109 color probe demonstrates why emitted feature queries and computed values still require visual runtime verification.

The Chrome 109 `ChatPage` now passes a lightweight branded text fallback into `AppInitializer` as well as its inner `Suspense` boundary. This avoids rendering the shared logo-based `LoadingScreen` during authenticated account/inbox initialization; the default modern shell still uses the existing logo screen. High-resolution logo assets remain emitted for lazy login. The compatibility fallback for the React Flow attribution background is explicitly set to sRGB in the legacy palette; its `color-mix()` enhancement remains guarded by Lightning CSS feature queries. This is source/build evidence only; confirm requested image assets in the Chrome 109 network panel on the target machine.

Set `CHROME109_SMOKE_RUNS` (1–10), `CHROME109_SMOKE_WIDTH`, `CHROME109_SMOKE_HEIGHT`, `CHROME109_SMOKE_CPU_RATE`, `CHROME109_SMOKE_LATENCY_MS`, and optional `CHROME109_SMOKE_DOWNLOAD_BPS` / `CHROME109_SMOKE_UPLOAD_BPS` (bytes per second; `-1` means unlimited) to capture repeatable timing samples. The mock never binds outside loopback and is only a frontend contract fixture: it does not model database transactions, Rails/auth-service semantics, WebSockets, production authorization or message delivery.

### Build a separate staging image (build only; no deploy)

The existing `Dockerfile` intentionally continues to build and serve `dist/`. `Dockerfile.chrome109` is a separate image recipe that builds and copies only `dist-chrome109/`, requires explicit CRM/Auth origins and an explicit compatibility-host allowlist at build time, and sets the Nginx runtime profile to production. The origins and allowlist become part of this static image, so build a new image for each staging environment. Do not pass credentials or production origins as build arguments. The client-side gate still rejects the known production CRM hosts even if listed. Example with reserved `.test` domains:

```sh
docker build -f Dockerfile.chrome109 -t sofia-frontend-chrome109:staging \
  --build-arg VITE_API_URL=https://crm-api.staging.example.test \
  --build-arg VITE_AUTH_API_URL=https://auth.staging.example.test \
  --build-arg VITE_WS_URL=wss://crm-api.staging.example.test/cable \
  --build-arg VITE_COMPAT_ALLOWED_API_HOSTS=crm-api.staging.example.test,auth.staging.example.test \
  .
```

This image recipe has not been built in the current host because Docker is unavailable. It has not been pushed, attached to Coolify, assigned a URL, or connected to any CRM API. Staging still requires a disposable backend with synthetic records, TLS, explicit host review and a separate deployment plan.

The API origins and host allowlist are compiled into the static JavaScript during the image build. Runtime `VITE_*` variables cannot change those compiled values; build a distinct image for each staging destination. The entrypoint remains in the image for the existing Nginx/CSP behavior, but it does not make the compatibility profile's compiled API policy runtime-configurable.
